## 1. 제품 목표

완벽주의 성향 사용자가 목표를 전부 달성하지 못했더라도, 기록 안의 작은 시도를 확인하고 다음 행동을 시작하기 쉽게 만든다.

MVP는 아래의 게스트 사용자 여정을 먼저 완성한다.

```text
목표 Markdown + 실제 기록 + 대상 닉네임
        ↓
목표 파싱 + 대상 발화 추출
        ↓
시도 신호 및 일치 근거 확인
        ↓
원문을 보존한 규칙 기반 다음 행동 제안
```

이 문서는 PRD에 있는 장기 기능 전체를 현재 구현으로 간주하지 않는다. 인증, 저장, AI 제공자, 구독, 커뮤니티, 오프라인 동기화는 이 범위에 포함하지 않는다.

## 2. 저장소와 현재 구현

| 관심사 | 저장소 구현 | 현재 계약/한계 |
| --- | --- | --- |
| 웹 앱 | Next.js 16 App Router, React 19, strict TypeScript | `src/app/page.tsx`, `src/app/layout.tsx`, `src/app/globals.css` |
| Markdown | `parseMarkdown` | Front Matter, 인용구, 체크리스트를 파싱. `quotes`, `todoItems`, `frontMatter`, `rawBody` 반환 |
| 발화 분리 | `splitScriptByUser(script, nickname)` | 볼드, 대괄호, `닉네임:` 표기에서 지정 닉네임 발화를 추출 |
| KPI | `evaluatePurpleKpi(nickname, parsedGoal, speeches)` | 키워드/트리거 기반 규칙 신호 및 근거 문장 반환. 의미 해석이나 완료 증명은 아님 |
| 데모 분석 | `analyzeDemoSession(goal, log)` | 현재는 닉네임 `Demo`를 내부에서 고정하고 자유문 각 줄을 Demo 발화로 감쌈 |
| 처방 | `DemoPrescription` | `originalTarget`, `fiveYearOldVersion`, `cheatKeyAction`, `phonicsSound`의 로컬 템플릿 |
| UI | 단일 게스트 화면 | 샘플 불러오기, 목표/기록 입력, 분석 버튼, 처방/KPI 결과. 현재 닉네임과 원본 화자 파싱 상태는 입력/표시하지 않음 |
| 영속성 | 없음 | 입력은 React 메모리 상태에만 있고 새로고침하면 사라짐 |
| AI | 제품용 연결 없음 | 데모 처방은 규칙 기반이며 외부 모델 호출을 하지 않음 |
| 데이터베이스 | Supabase 원격 DB | 현재 앱 게스트 분석은 DB를 사용하지 않음. 운영 테이블과 권한은 [문서 14](14_SUPABASE_PROJECT_STATUS.md) 참고 |

코드와 PRD가 다를 때는 먼저 위 구현을 사실 기준으로 취급한다. 제안된 기능을 구현 완료로 문서화하지 않는다.

## 3. 사용자 경험 명세

### 3.1 입력

MVP 입력 화면은 세 가지를 제공한다.

1. **목표 Markdown:** 자유 텍스트. 일반 문장은 목표 인용구로 처리하고, 명시적 `> 목표`, `- [ ] 할 일`, `- [x] 완료` 및 지원 Front Matter는 원문 그대로 파서로 보낸다.
2. **실제 기록:** 다중 화자 형식의 대화록을 입력한다. `**닉네임**: ...`, `[닉네임]: ...`, `닉네임: ...` 표기를 지원한다.
3. **대상 닉네임:** 대화록에서 분석할 화자를 지정한다. 닉네임은 앞뒤 공백을 제거하고 대소문자를 구분하지 않는 기존 splitter 계약을 따른다.

입력 예시:

```md
---
persona: easy_peasy
---
> 매일 영어 회화 한 문장 완벽하게 외우기
- [ ] 오늘 한 번 소리 내어 읽기
```

```text
**Sara**: 오늘 스트레칭을 완료했어요.
**EasyPeasy**: 한 문장을 세 번 읽었어요. 완벽하진 않았지만 시도했어요.
Rina: 다음에는 저도 해볼게요.
```

예시 체험은 위와 같은 실제 다중 화자 입력 및 대응 닉네임을 함께 채워야 한다. 사용자 기록의 모든 줄을 대상 화자의 발화인 것처럼 조용히 변환하지 않는다. 단문 자유 기록 모드가 필요하면 명시적인 입력 모드로 구분하고, 내부에서 해당 텍스트를 어떻게 해석했는지 사용자에게 보여준다.

### 3.2 분석 결과

결과 영역은 아래 정보를 서로 구분해 표시한다.

- **목표 추출:** 원문 quote와 체크리스트, 파싱된 목표가 없을 때의 안내.
- **기록 추출:** 전체 화자 로그가 아닌 선택된 닉네임의 발화만 표시하고, 추출된 발화 수를 제공.
- **시도 신호:** KPI 엔진의 현재 규칙 결과. 일치/미일치와 판정 근거를 표시.
- **다음 행동:** 원문 목표를 보존한 로컬 템플릿 기반 완화 문구, 즉시 실행할 행동, 시작 신호.
- **한계 고지:** 키워드/트리거 매칭 결과는 실제 완료 증명이나 문맥 이해가 아니며 AI 생성도 아님을 명시.

“시도 신호”를 “성취 확정”, “완료 증명” 또는 임상·심리 평가로 표기하지 않는다. 일치율이 실제 달성률처럼 오해될 수 있으면 퍼센트 대신 일치 문장 수와 근거를 우선 제시한다.

## 4. 구현 경계 및 데이터 계약

### 4.1 분석 함수

UI에서 분석을 분리하고, `src/demo/demoSession.ts`에 다음 입력/결과 계약을 둔다. 실제 타입 이름과 필드는 구현 시 기존 스타일과 공개 core 타입을 확인하여 결정한다.

```ts
interface DemoSessionInput {
  goalMarkdown: string;
  conversationLog: string;
  targetNickname: string;
}

interface DemoSessionResult {
  parsedGoal: ParsedMarkdown;
  targetNickname: string;
  extractedSpeeches: UserSpeech[];
  report: KpiMatchReport;
  prescription: DemoPrescription;
}
```

계약 원칙:

- 입력된 대화록은 `splitScriptByUser`에 원문 그대로 전달한다.
- 대상 닉네임을 정규화하고 비어 있으면 명시적 validation error를 반환한다.
- quote와 todo를 합친 목표 문맥을 KPI 판정에 제공한다. 표시용 원문 선택은 판정 입력을 축소하지 않도록 한다.
- 목표가 없거나 대상 발화가 없을 때 성공처럼 보이는 fallback 결과를 생성하지 않는다.
- 분석은 순수 클라이언트 로직으로 유지하고 네트워크/DB/API를 호출하지 않는다.
- 원본과 분석 결과는 화면 메모리 상태에서만 사용한다.

`DemoPrescription`은 현 데모의 네 필드 계약이다. PRD의 `AiPrescriptionSchema`(simplified/cheat/sensory/actionPlan/confidence)와 이름·의미가 다르다. MVP 구현에서 두 스키마를 무리하게 합치거나 DB 저장용 schema로 취급하지 않는다. AI 제품 통합은 provider, 응답 검증, secret 경계와 출력 정책을 별도 결정한 후에 한다.

### 4.2 페이지 컴포넌트 경계

현재 단일 페이지 구조를 우선 유지한다. 상태 및 표시를 분리해야 할 때만 작은 컴포넌트로 추출한다.

```text
src/app/page.tsx
  입력 상태, 예시 로드, 제출/오류 상태 조정
  InputPanel
  ParsedGoalPreview
  ExtractedSpeeches
  PrescriptionResult
  AttemptEvidence

src/demo/demoSession.ts
  Markdown parse → nickname split → KPI evaluate → local template

src/core/parser/mdStaticParser.ts
src/core/splitter/scriptSplitter.ts
src/metrics/purpleKpiEngine.ts
```

`InputPanel` 등은 구현을 위한 개념적 경계이며, 사용 사례가 생기기 전 별도 디렉터리나 상태관리 라이브러리를 미리 추가하지 않는다. 도메인 처리를 JSX 내부에 복제하지 않는다.

## 5. 화면 상태와 오류 계약

| 상태 | 조건 | 사용자 표시/동작 |
| --- | --- | --- |
| 시작 | 아직 분석하지 않음 | 입력 안내와 예시 체험 표시 |
| 입력 편집 | 입력 변경됨 | 기존 결과가 현재 입력과 다르다는 점이 분명해야 함. 이전 결과가 혼란을 주면 지우거나 “다시 분석 필요”로 표시 |
| 검증 오류 | 목표 quote/todo 없음, 닉네임 공백/미설정 등 | 오류 필드 인근에 수정 가능한 메시지. 결과/성취 배지를 표시하지 않음 |
| 추출 결과 없음 | 유효한 목표이나 대상 화자 발화 없음 | “해당 닉네임의 발화를 찾지 못함”과 지원 표기 예시 표시 |
| 미일치 | 발화는 추출했으나 KPI match 없음 | 신호 미발견 상태. 기록을 바꾸거나 시도를 추가할 수 있음 |
| 신호 발견 | 한 개 이상 KPI match | 일치한 실제 문장과 이유를 보여주고 “시도 신호”로 안내 |
| 예외 | 예상하지 못한 분석 실패 | 성공형 결과를 만들지 않고 재시도/입력 점검을 안내. 원문 기록이나 secret은 콘솔에 쓰지 않음 |

에러 응답은 현재 코드의 예외 처리 방식을 따르되, 분석 실패를 빈 처방이나 성공 상태로 대체하지 않는다. 입력 변경 때 stale 결과가 제출 결과인 것처럼 남지 않도록 테스트한다.

## 6. KPI 정확성 가드레일

기존 `purpleKpiEngine.ts`는 목표 문구의 단어 일부 또는 `완료`, `했습`, `읽었`, `포기 안`, `성공` 트리거 포함 여부로 match를 만들 수 있다. 따라서 다음을 구현 및 테스트에서 지킨다.

- 모든 추출 발화를 같은 기준으로 평가하고, 첫 일치 근거 외의 추가 match도 손실 없이 반환한다.
- UI가 근거 문장과 `reason`을 결과에 제공한다.
- 다른 화자의 행동 문장, 인용된 제3자 문장, 목표와 무관한 일반 단어가 잘못 match되는 사례를 회귀 테스트로 검토한다.
- “아무 기록이나 완료 단어가 있으면 달성” 같은 동작이 제품 의도인지 확정되지 않았으므로, 기존 엔진의 과도한 트리거 동작을 UI에서 실제 완료로 과장하지 않는다.
- KPI 알고리즘 변경은 별도 로직 변경으로 취급하고 기존 테스트/PRD 규칙과 함께 검토한다. 이번 문서만으로 판정 임계값을 바꾸지 않는다.

## 7. 접근성·반응형 기준

- 모든 입력에 시각적 label과 프로그램상 이름을 제공한다.
- 분석은 키보드로 실행 가능해야 하며 focus indicator를 숨기지 않는다.
- 오류는 `role="alert"` 등 적절한 방식으로 전달한다. 결과 업데이트는 하나의 적절한 live region을 사용하여 전체 카드 내용을 과도하게 읽지 않게 한다.
- 색상이나 아이콘만으로 성취/오류 상태를 구분하지 않는다.
- 모바일 폭에서 입력 순서가 목표 → 기록 → 닉네임 → 분석 → 결과 순서를 유지한다.
- 애니메이션을 추가한다면 `prefers-reduced-motion`을 존중한다.
- 사용자가 입력한 Markdown은 HTML로 해석해 렌더링하지 않는다. 결과는 텍스트로 안전하게 표시한다.

## 8. 보안·개인정보·인프라

- 기본 게스트 분석은 브라우저 안에서만 실행된다. 사용자 입력이 포함된 fetch, Supabase insert, analytics 이벤트를 추가하지 않는다.
- 입력값을 telemetry, error report, debug log, URL query에 넣지 않는다.
- 샘플 데이터는 고정된 공개 예시이며, 실제 사용자 기록과 구분한다.
- 새로고침 후 입력 복원은 하지 않는다. persistence가 필요해지면 범위, 동의, 저장·삭제, 브라우저 공유 환경 위험을 먼저 정의한다.
- Supabase 원격 스키마와 권한은 PRD의 예시 SQL보다 운영 사실을 우선한다. 애플리케이션 로그인/쓰기 기능을 이 범위에서 추가하지 않는다.
- GitHub webhook receiver는 앱의 목표·대화록 API가 아니다. HMAC 검증 및 서비스 이벤트의 비공개 저장 계약을 유지한다.
- Vercel 정적/웹 배포는 앱 코드에 필요한 데이터 전송 경계를 바꾸지 않는다.

## 9. 작업 분해와 완료 게이트

각 항목은 별도 작은 작업으로 구현하며, 게이트를 통과하기 전에 다음 항목을 완료로 표시하지 않는다.

### MVP-A: 입력 형식 명확화

- [ ] 자유문 로그와 다중 화자 대화록을 구분하고 사용자가 분석 닉네임을 지정할 수 있다.
- [ ] 기존 예시 체험은 다중 화자 샘플 및 해당 닉네임을 함께 입력한다.
- [ ] 대화록 원문을 변형 없이 splitter에 넘긴다.
- **검증:** 볼드/대괄호/plain colon, 다른 화자 제외, case-insensitive nickname을 함수 테스트로 검증.

### MVP-B: 파싱 투명성

- [ ] 인용구, 할 일, 체크 완료 여부와 Front Matter를 결과에서 확인한다.
- [ ] 파싱 가능한 목표가 없는 경우 판정을 실행하지 않고 안내한다.
- [ ] 입력 형식의 지원 범위를 UI에서 설명한다.
- **검증:** plain text, quote, checklist, Front Matter, 빈 입력 및 잘못된/미폐쇄 frontmatter를 테스트.

### MVP-C: 판정 근거와 오탐 경계

- [ ] 추출 발화와 각 match 근거를 노출한다.
- [ ] 빈 로그, 대상 화자 없음, 발화 미일치, 단일/복수 match 결과를 구분한다.
- [ ] 퍼센트가 달성률로 오해되지 않게 UI 문구/시각화를 검토한다.
- **검증:** positive/negative 및 cross-speaker 사례 추가. KPI 엔진의 알려진 트리거 한계를 UX 고지에 반영.

### MVP-D: 실행 가능한 규칙 기반 처방

- [ ] 원문 목표를 손상 없이 노출한다.
- [ ] 템플릿 완화 문구 및 즉시 행동이 입력 목표를 반영한다.
- [ ] 외부 AI가 생성한 것처럼 표시하지 않는다.
- **검증:** 완벽주의 수식어 제거/공백/대체어 없음 등 템플릿 경계 사례.

### MVP-E: 시연 적합성

- [ ] Desktop과 mobile 화면에서 입력/결과 흐름 확인.
- [ ] 키보드 및 스크린리더로 입력, 제출, 오류 및 결과를 검증.
- [ ] Network 탭에서 사용자 기록이 원격으로 전송되지 않는지 확인.
- [ ] Vercel preview/production에서 데모 시나리오 확인.
- **검증:** 테스트, build, 수동 브라우저 체크리스트 완료.

## 10. 자동 검증 및 브라우저 확인

웹 변경 시 실행:

```bash
npm test -- --runInBand
npm run build
git diff --check
```

브라우저 시나리오:

1. 새 탭/로그아웃 상태에서 랜딩 화면과 예시 체험을 연다.
2. 결과의 원문, 파싱 정보, 대상 화자 발화, 신호 근거, 규칙 기반 처방을 대조한다.
3. 대상 닉네임을 바꿔 해당 발화가 없을 때의 안내를 확인한다.
4. 빈 목표, Markdown quote, checklist, 빈 로그, 목표와 무관한 로그로 오류·미일치·신호 상태를 확인한다.
5. 입력 변경 후 제출 전 이전 분석이 최신인 것처럼 표시되지 않는지 확인한다.
6. 새로고침 후 입력이 남지 않는지 확인한다.
7. Network 패널에서 분석 실행 중 사용자 입력 전송이 없는지 확인한다.
8. 모바일 viewport, 키보드 탭 이동, live announcement를 확인한다.

## 11. 후속 제품 결정이 필요한 항목

다음은 이 구현 상세서에서 확정하지 않는다.

- 로그인/무료 quota를 MVP에 포함할지, 비로그인 사용 경험 검증 후 진행할지
- 목표와 기록을 저장할 경우 보존 기간, 사용자 삭제, export, 공유 환경 고지
- AI 제공자를 쓸지, BYOK 방식의 키 노출 위험과 호출 모델을 어떻게 고지할지
- 한국어 형태소/의미 일치가 필요한지, 현재 KPI를 어떻게 보정할지
- peer 표현 공유의 공개 동의, moderation, spam 방지와 권한 구조
- 실시간 피드백 수집 목적/보존/공개 범위와 개인정보 고지
- 오프라인 저장과 서버 동기화를 제공할 때의 충돌 해결 및 rollback 의미

이 항목 중 하나를 구현할 때는 별도 요구사항과 데이터/보안 검토를 추가하고, 운영 Supabase 상태를 다시 확인한다.
